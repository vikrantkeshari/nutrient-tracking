Foundations

the constraints every screen obeys

This app is built for someone's parent, not for the person who wrote it. That single decision explains the 18px base font, the 66px input heights, the 70px buttons, and copy that says "They see every meal you eat" instead of "Sharing level: detailed". Match it.

Nothing is smaller than 44px

Most touch targets are 52–70px. Steppers are 66px squares because a thumb has to hit them reliably.

Two text tiers, both AA

--t1 white and --t2 #D5DAE3. There is no third, dimmer tier — it wouldn't pass on --card.

Colour never carries meaning alone

Macro bars are labelled. "Not sharing" gets a padlock as well as reduced opacity.

Say what happens, in plain words

"Is this right?" · "They see only your daily total" · "We could not analyze that — please fill the numbers in".

Errors are inline, never alerts

Red .err box above the form, or a toast above the nav. No alert().

Four tabs, and that's final

Today · Groups · Add · Me. New surfaces go inside an existing tab, not beside it.

Adding a meal

7 states · screens/AddMeal.jsx

The whole product thesis lives in this flow, and it has one non-negotiable property: it never dead-ends. Camera denied → file picker. AI down → the same review form, zeroed, with an honest message. There is no state where a user has eaten something and cannot record it.

Every correction is data

On save the client diffs each field against what the model returned. Any difference sets is_edited and writes the model's numbers to original_*. That's what makes AI accuracy a query instead of an opinion — and it's why the review screen must never be skipped, even when confidence is high.

6 screens · screens/Groups.jsx

The tab routes itself by how many groups you're in: zero shows join/create, one drops you straight into it, two or more shows a picker. Nobody navigates a list of one.

The detail screen renders three different ways at once

Members at detailed get a meal timeline. Members at totals get one card of daily numbers. Members at none are listed with a padlock and nothing else — visible as participating, which matters, without leaking anything.

No branch, at any level, has access to a photo. The shared views don't project the column.

Designed, not built

8 screens · all unclaimed

These eight do not exist in the codebase. They are specified here so that "build the history view" is a contained task with a known answer rather than an open design question. Each links to its issue in the backlog. Build them in the app's existing classes — .card, .item, .choice, .big — and no new ones unless a pattern genuinely repeats.

One rule for the Trends screen specifically

An earlier version of this app shipped a trends chart filled with Math.random() — in production, rendering as though it were real data. It was deleted rather than fixed. Show an empty state when there is no data. Never render a placeholder that a user could mistake for their own numbers.

Two things this gallery cannot show you

Meal photos

They're captured, compressed to ~25 KB, and uploaded to a private bucket — and then no screen renders them. signedThumbUrl() has zero call sites. Screen 11 shows the meal list as it exists today; adding a 52px thumbnail to each row is issue #3.

Motion

Every screen change is a 250ms fade (.fade), bars animate width over 500ms, and the toast slides up above the nav for 2.6 seconds. Keep transitions on width and opacity — nothing in this app moves in a way that would need prefers-reduced-motion to be turned off.

Fidelity note. Every frame above is real markup styled with a scoped copy of frontend/src/styles/variables.css and index.css, scaled to 82%. Nothing here is a redraw, so what you see is what the classes actually produce. If you change the app's CSS, change the copy in this file's <style> block too — a spec that has drifted from the product is worse than no spec.
